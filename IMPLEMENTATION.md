# Truss Implementation

The stage0 compiler is written in OCaml and is compiled to a static binary. When
the Truss compiler builds a program it emits C code as its backend. Truss
programs do not link to a separate runtime, they use libc. Truss packages
compile to a single binary or library.

## Modular Design

Each part of Truss should be modular. This will help make the compiler easier to
develop as well as make it easier to bootstrap the compiler in parts.

## Notes for stage0

### Building

- **Dependencies** are declared in `dune-project`, which generates
  `truss.opam`. Install them with
  `opam install . --deps-only --with-test --with-dev-setup`. On macOS, Zarith
  also needs GMP and `pkgconf` from Homebrew.
- **`dune build`** builds everything, **`dune test`** runs the tests, and
  **`dune fmt`** formats the code with the ocamlformat version that
  `.ocamlformat` pins.
- **CI** (`.github/workflows/ci.yml`) builds, checks formatting, checks that
  `truss.opam` matches `dune-project`, and runs the tests, on every pull
  request and every push to `main`.

### Documents

A design document describes the design as it is. How it got there belongs in
version control, in commit messages and pull request descriptions. A
document has no sections that list what changed, what an earlier version
did, or which review settled what; when the design changes, the document is
rewritten to describe the new design.

### Testing

Every stage of stage0 is tested the same way:

- **A test states what it checks.** Each test gives a small input and asserts
  exact facts about the result: the tokens, a diagnostic's code and
  position, the text after applying a fix. Its name says what behavior it
  covers.
- **Tests are fast and deterministic.** No randomness, no large inputs, and
  no test cases generated by combining options. The whole suite runs in
  milliseconds, so it can run on every change.
- **No golden files.** A golden file compares a whole dump of output, so it
  breaks when anything in the dump changes, whether or not the behavior it
  meant to check did, and it never says which fact mattered.
- **Fuzzing and benchmarks are tools, not tests.** They live in
  `stage0/tools/` and are run by hand. Each problem a fuzzer finds becomes a
  focused test of its own.
- **Checks against the documents are tests,** as long as each one states a
  single property, such as "GRAMMAR.md's keyword list matches the lexer's",
  or "every example in the documents lexes cleanly".

These notes collect implementation consequences of the decisions in
[DESIGN.md](DESIGN.md), [SYNTAX.md](SYNTAX.md), and [GRAMMAR.md](GRAMMAR.md).

### Lexer

The full design is in [LEXER.md](LEXER.md), and the lexer is built in
[`stage0/`](stage0). In short:

- **Hand-written, as a pipeline of two stages.** A scanner turns bytes into
  raw tokens that record whether a line break came before them, and a layout
  stage pulls them one at a time, inserts `NEWLINE` tokens, and matches
  brackets.
- **Unicode tables generated from one pinned Unicode version,** rather than
  taken from sedlex or `uucp`, whose versions follow their own releases. Names
  are ASCII, so the tables only find words and forbidden characters.
- **Integer literals do not fit OCaml's `int`,** which has 63 bits. Store them
  with Zarith, which the prover's exact integer arithmetic needs anyway. Float
  literals are kept as exact decimals until the type checker rounds them.

### Parser

The full design is in [PARSER.md](PARSER.md). In short:

- **A hand-written recursive-descent parser** that never backtracks. It parses
  operators with a total order and then reports the combinations Truss's
  partial order leaves out, with exact parentheses as fixes.
- **One tree per definition, with positions relative to it.** The lexer's
  balanced brackets let a file be split into definitions before parsing, so
  each definition parses on its own, and one that only moved gives the same
  tree.
- **An abstract tree, not a lossless one.** Truss has no comments, so the
  formatter needs only spans, blank lines, and parentheses from the source.
- **`grammar/truss.mly` as a reference.** A Menhir parser built from it, for
  tests only, must accept and reject the same files as the real one.
- **Diagnostics in a structured format,** with exact text replacements for
  fixes, shared with the lexer.

### Hashing and caching

- **Deterministic CBOR** (RFC 8949, section 4.2) is small enough to write
  directly, which keeps the exact byte format under the project's control. The
  same encoder must later be written in Truss and produce the same bytes.
- **BLAKE3** for content hashes. `digestif` provides BLAKE2 but, as far as I
  know, not BLAKE3, so stage0 needs a binding or its own implementation. Every
  hash carries a prefix naming the format version and algorithm, so this can
  change.
- **A content-addressed store** of results, each with the trace of what it
  depended on, can start as files in a cache directory named by hash.
  Each compiler stage has its own version in the key.

### Background process

- **Starting fresh on every command costs O(files),** because the compiler must
  at least check which files changed. A long-running process that watches the
  files (FSEvents on macOS, inotify on Linux) and keeps parsed definitions and
  traces in memory makes each command O(change). The language server and the
  command line can share it.

### Code generation through C

The full design is in [CODEGEN.md](CODEGEN.md). In short:

- **Why C rather than QBE.** Truss has no foreign code, so the standard
  library's hashing, crypto, and text handling run on Truss's own generated
  code, and nothing can drop to C for speed. QBE has no inliner, no 128-bit
  multiply, no bit-counting, rotate, or byte-swap instructions, no `sqrt`, no
  SIMD, no atomics, and no way to say that pointers do not alias. C compilers
  have all of these. Truss proves no aliasing, which C expresses with
  `restrict`. Linking libc already needs the platform's C toolchain, so
  emitting C adds almost no dependency.
- **A lowered IR in front of C.** Monomorphization, drops, yield lowering, and
  cursor state machines happen in the compiler's own IR. Early cutoff compares
  that IR, never object code, so a different C compiler version invalidates no
  proofs or test results.
- **Generated C avoids undefined behavior by construction.** It is compiled
  with `-fwrapv`, so arithmetic wraps even if the prover were wrong about an
  overflow, and shift amounts are masked. Indexes and division are always
  proven. The compiler passes `-fno-strict-aliasing`,
  `-fno-finite-loops`, because a pure loop without a `time` clause may
  legitimately never end, and `-ffp-contract=off` with no fast-math, so floats
  follow IEEE 754 bit for bit.
- **Overflow checks use compiler builtins,** such as
  `__builtin_add_overflow`. Proven-safe arithmetic needs none.
- **Positions stay relative to each definition.** Locations for panics,
  `echo`, and failed asserts come from the position table built at the end of
  the build. Release builds may also emit `#line` directives for debuggers and
  profilers.
- **Linking is O(program).** It is the one step of an everyday edit whose cost
  grows with the whole program. Stage0 links in full every time, with a fast
  linker: lld or mold on Linux, and the system linker on macOS. Making it
  incremental is deferred. The likely way is a long-running test runner that
  keeps the program loaded, loads only the definitions that changed as a
  small shared library, and forks test workers from itself. Truss has no
  mutable global state, so swapping code in a running process needs no state
  to be carried over.

### Proofs

- **A pinned SMT solver with step limits.** Z3's `rlimit` and cvc5's
  `--rlimit` count work rather than time, so a proof gives the same answer on
  every machine as long as the solver version and options are the same. Both
  are part of the prover's version in cache keys.

### Running code while compiling

- **No interpreter: compile and run, through the test runner.** Tagged
  template checks, the values of templates without interpolation, and the
  tables of `Map` and `Set` constants are computed by compiling the
  functions involved and running them in the test runner's workers. Those
  functions are pure and proven to terminate, so a run needs no step limit
  and cannot panic. A stack overflow is reported as an error.
- **The standard library's checkers ship compiled** with the toolchain, for
  each host and for both widths of `USize`. Dependencies' checkers are
  compiled once per version. Only a tag defined in the package being edited
  costs a compile, and only when its check changes. Results are cached by
  the checker's hash and the literal text.
- **Code built to run while compiling uses the target's `USize`,** which is a
  `typedef` in the generated C, so cross-compiling from a 64-bit host to a
  32-bit target gives the target's results.
- **Results become static data** through a walker generated for each type,
  which writes the value out as C initializers.
- **Constant arithmetic needs no running code.** Integers are exact, with
  Zarith. Float operations in constants are the exact IEEE ones, which OCaml
  computes bit for bit. `Float32` is computed in 64 bits and rounded to 32,
  which gives the correctly rounded 32-bit result for `+`, `-`, `*`, `/`,
  and `sqrt`, because 53 bits is more than twice 24 plus 2.
